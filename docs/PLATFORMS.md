# Platform setup and build notes

This file records exactly how the Android and iOS targets in this repository
were produced, what is verified, and what still has to be done on a machine
with the real toolchains. **Nothing here has been compiled** — there is no
Flutter SDK, Android SDK or Xcode in the environment this project was authored
in, so the platform files are structurally written but never executed.

### One-time step: the Gradle wrapper JAR

`android/gradle/wrapper/gradle-wrapper.jar` is **absent and cannot be
fabricated** — it is a binary. The properties file and the `gradlew` scripts
are present; the JAR is the one thing a text-only authoring environment cannot
produce. On a machine with Gradle installed, run either:

```bash
cd android && gradle wrapper --gradle-version 8.7
```

or simply open `android/` in Android Studio and let it sync, which writes the
JAR for you. `./gradlew` works normally afterwards.

### Firebase is opt-in

The `google-services` and Crashlytics plugins are applied only when the build is
given `-PenableFirebase=true`:

```bash
flutter build apk --release -PenableFirebase=true
```

Without the flag the app compiles against the no-op analytics and crash
reporting implementations in `lib/core/services/`, and it works fully offline.
`android/app/google-services.json` is git-ignored and must be supplied by
whoever enables Firebase. Dart-side initialisation is additionally gated behind
`AppConfig.enableFirebase` (a `--dart-define`) and wrapped in `try/catch`, so a
missing or malformed config file degrades to no-op telemetry rather than a
launch crash.

## iOS

The iOS target was **rendered from the upstream Flutter template** rather than
hand-written: `packages/flutter_tools/templates/app/ios.tmpl/` at git ref
`stable` was fetched and rendered with these values:

| Template variable | Value |
| --- | --- |
| `projectName` | `merge_drop` |
| `iosIdentifier` | `com.mergedrop.merge_drop` |
| `withSwiftPackageManager` | `false` |
| development team | *(unset — set it in Xcode)* |

The resulting `ios/Runner.xcodeproj/project.pbxproj` was audited
programmatically: 56 definitions, 56 unique object ids, 0 duplicates, 0
dangling references, balanced braces and parentheses, all 14 required `isa`
types present.

What the upstream template implies and what was kept:

- **Implicit Flutter engine.** `AppDelegate.swift` adopts
  `FlutterImplicitEngineDelegate` and `SceneDelegate.swift` owns the
  `FlutterViewController`. There is no `AppDelegate`-owned window and no
  `GeneratedPluginRegistrant` registration in the app delegate.
- **Swift Package Manager is off**, so plugins resolve through CocoaPods.
  `ios/Podfile` is generated by `flutter build ios` / `flutter run`.
- `IPHONEOS_DEPLOYMENT_TARGET = 15.0`.
- `objectVersion = 54`.
- Runner build phases: Run Script → Sources → Frameworks → Resources →
  Embed Frameworks → Thin Binary. The `embed` step lives inside Thin Binary.
- RunnerTests has only Sources and Resources phases and uses
  `GENERATE_INFOPLIST_FILE = YES`.
- Storyboards are `PBXFileReference`s (`name = Base;
  path = Base.lproj/Main.storyboard`) plus a matching `PBXVariantGroup`.
- There is deliberately **no** root `ios/Runner/Assets.xcassets/Contents.json`
  — the upstream template does not ship one either.

### App icons and launch image

`ios/Runner/Assets.xcassets/AppIcon.appiconset/` holds 15 PNGs named
`Icon-App-<size>@<scale>x.png`, and `LaunchImage.imageset/` holds 3 PNGs
(`LaunchImage.png` at 1x/2x/3x). Both were generated by
`tool/generate_icons.py` and every entry was checked against the upstream
`Contents.json`: each `size × scale` equals the PNG's pixel size, every image is
`mode = RGB`, and **none carries an alpha channel** (App Store uploads reject
alpha in app icons).

### Info.plist

Portrait only (`UISupportedInterfaceOrientations` lists just
`UIInterfaceOrientationPortrait`). `GADApplicationIdentifier` is set to Google's
public **test** app id; a production id must be supplied via a build
configuration, never committed. `ITSAppUsesNonExemptEncryption` is `false` and
`NSUserTrackingUsageDescription` is present.

## What has **not** been verified

Be explicit about this with anyone picking the project up:

- `flutter pub get` has never run, so no package has been resolved.
- `flutter analyze` has never run. `tool/check_sources.py` is a structural
  analyser (import resolution, brace/paren balance, domain-layer purity,
  placeholder bans, undefined-identifier and missing-receiver detection) — it is
  **not** a Dart compiler and cannot catch type errors.
- `flutter test` has never run. The six Dart test files under `test/` have never
  been executed.
- No Android or iOS build has been produced. No app has been installed or run.
- The pure-Dart domain logic *has* been executed, but through a Python mirror in
  `tool/mirror/` (113 tests, all passing) rather than through Dart itself. See
  `docs/TESTING.md`.
- The 500-level catalogue has been validated by simulating it with the Python
  mirror (`python3 tool/mirror/validate_levels.py` → 0 errors, 0 warnings), not
  by playing it.

First commands to run on a real machine:

```bash
flutter pub get
cd android && gradle wrapper --gradle-version 8.7 && cd ..
flutter analyze
flutter test
flutter run
```
